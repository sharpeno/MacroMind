建议按下面的边界安排：

| 可并行工作               | 现在可以做什么                                       | 与另一边如何隔离                                   |
| ------------------------ | ---------------------------------------------------- | -------------------------------------------------- |
| **任务运行框架**         | 实现任务创建、状态、失败重试、运行日志及独立输出目录 | 用测试材料开发，不修改正式数据和审阅记录           |
| **大模型接入与用量记录** | 接入一个模型，记录模型版本、token、耗时和调用失败    | 不依赖分析框架定稿；真实调用需要可用的模型服务配置 |
| **已有能力的工具封装**   | 将读取材料、查询证据、引用校验、审计封装为统一接口   | 读取已封存版本，结果写入新的任务目录               |
| **最小操作界面**         | 输入问题、上传任务材料、查看进度、展示结果和证据     | 任务上传区与另一边的正式材料导入区分开             |
| **部署与启动流程**       | 整理配置、依赖、启动入口、日志和备份恢复             | 在独立开发目录验证，不改正在使用的环境             |
| **评测及申报资料框架**   | 定义耗时、引用正确率、人工修改量等指标，整理佐证清单 | 先建立记录方式，不提前填写效果数字                 |

**最值得先做的是“任务运行框架＋工具接口＋模型接入”。** 这是此前评估中最关键的产品缺口，也最少依赖正在进行的人工审阅。界面可以随后接上，避免先做出页面却没有真实执行能力。

有几项工作建议继续留在另一边，暂时不要同时改：

- 正式材料导入、归一化和人工反馈接收。
- 方法规则的增删、冻结和语义验收。
- 当前版本指针、正式证据索引与封存清单。

并行开发时，约定一个简单规则就够了：**每个任务固定读取某一份已封存的数据版本和方法版本，运行过程中不追随“最新版本”；新结果另存，不能回写原材料。** 另一边完成新一轮审阅后，再显式切换版本做集成验证。

第一阶段的验收目标可以定为：

> 在独立开发环境中，用户提交问题和一份测试材料，系统实际调用模型及证据工具，生成带来源的结果，并保存完整任务记录；原有材料、审阅结果和冻结规则不变。

这个阶段能验证产品执行链路，分析质量则继续由另一边的审阅和评测推进。它们可以同时进行，也不需要现在就引入多智能体、多个模型或一体机。
