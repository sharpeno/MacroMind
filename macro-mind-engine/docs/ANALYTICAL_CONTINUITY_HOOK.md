# Human-Reviewed Analytical Continuity Hook

`ContinuityAnnotation` is an independent engineering object. It is neither an AuditRecord nor a Frozen Ontology object, and is not added to ontology schemas, registry vocabularies or schema exports.

Its intended future use is to study how **the same analytical question, at multiple times, produces changes in Judgment as the Information Set changes**. Phase 1.5A implements no Evidence Delta, Judgment Delta, or Thread construction. It does not discover relationships using titles, keywords, similarity, embeddings, or language models.

## Human input contract

The caller explicitly supplies subject_ref, related_ref and one relation_type. Allowed human labels are SAME_ISSUE_CANDIDATE, NEW_EVIDENCE, REPEAT_EVIDENCE, COUNTER_EVIDENCE, THESIS_REFINEMENT, FORECAST_UPDATE, METHOD_REUSE and UNCERTAIN_RELATION. No label is selected automatically.

The default review_status is UNREVIEWED; CANDIDATE, CONFIRMED and REJECTED are also allowed. Review status never advances automatically. CONFIRMED requires an explicitly supplied nonblank reviewer and resolved references. The caller is responsible for providing the actual observer identity; no system/model/person identifier is defaulted.

The caller supplies `known_refs`, the explicit set of actual artifact/object/episode references it has resolved. This is a resolution boundary, not discovery or a guarantee that arbitrary caller assertions are true. The object computes RESOLVED only when subject_ref, related_ref and any explicitly provided thread_ref are in that set. Missing references remain UNRESOLVED, even if the caller tries to claim resolution. Candidate/unreviewed records can be retained for later review. They are never guessed or silently confirmed. To re-evaluate, reconstruct the annotation with a newly resolved context; a serialized annotation alone is not proof of resolution.

`thread_ref` defaults to null and is never generated. A human can record a candidate relation between two episodes without creating a formal thread. An existing thread reference can be supplied explicitly and is checked against the caller's known references.

```python
from macromind.audit import ContinuityAnnotation

candidate = ContinuityAnnotation(
    subject_ref="episode:2026-01",
    related_ref="episode:2026-09",
    relation_type="SAME_ISSUE_CANDIDATE",
    known_refs={"episode:2026-01", "episode:2026-09"},
    review_notes="Human-entered candidate; no formal thread yet",
)
assert candidate.review_status == "UNREVIEWED"
assert candidate.thread_ref is None
```

## Identity and operational time

`annotation_id` is a stable SHA-256 identity of subject_ref, related_ref, relation_type and reviewer. Changing relation_type creates a new identity. Supplying an incompatible identifier is rejected. `created_at` is optional caller-supplied operational time; it does not affect annotation identity or `semantic_hash()`. Review status, notes, evidence and resolution are retained in the semantic hash. The normalizer does not include annotations in audit bundle output, so annotation timestamps cannot affect AuditRecord IDs or bundle hashes.

Tests cover nullable threads, default unreviewed state, explicit human confirmation, blank reviewer rejection, unresolved references, relation identity, operational timestamp exclusion, and two very similar input analyses producing **zero** automatic annotations and **zero** automatic threads. No ContinuityAnnotation is generated by the acceptance normalization run.
